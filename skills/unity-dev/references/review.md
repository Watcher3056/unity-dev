# Review (stage 6)

Part of the unity-dev skill, read by the main thread and the reviewer (SKILL.md, **Skill files by role**). The stage itself is [PIPE-REVIEW] in SKILL.md; these are its rules. The depth of the review follows the task's profile ([PROFILE-STAGES] in [profiles.md](profiles.md)).

- A reviewer sub-agent that didn't write the change reviews the diff and answers the "Impact and safety" questions ([findings.md](findings.md)). It gives every finding a status and checks it by the ladder there, up to the Editor level.
- [REV-ORDER] **Order:** the reviewer first reviews without Unity (reading). Meanwhile the tester builds the base setup: the stage-2 reproduction and what the change obviously touches. When the base setup is ready, the reviewer runs the checks that need the Editor, if any ([WHO-RUNS] in [agents.md](agents.md)): its report names them and why, or says it needs none, and then Unity stays with the tester.
- [REV-DATA] **The reviewer reads the project's data; QA checks what the game does.** The reviewer may run Editor scripts in batch mode that read data: what an imported file contains, import settings, resolved prefab values, etc. It doesn't open scenes or the tester's setups, enter Play Mode or play scenarios; anything that needs a scene or the running game goes to QA as an open finding.
  - Example: a script reads what an imported file contains → the reviewer does it; etc.
  - Anti-example: the reviewer opens the test setup and plays the scenario to see whether it breaks → that's QA's job; hand it over instead; etc.
- [REV-SHARED] **Shared things:** when the change touches something others use too (an asset, a layer, a config, a base class, a shared component, etc.), list its users and state for each what it does before → after. The question is "what changes for this user", not "does this user have what the fix is about".
  - Example: a shared filter was changed to fix screen X, and screens Y and Z use it too → what do Y and Z show before and after?; etc.
  - Anti-example: "the other users don't have the property the fix targets, so they're unaffected", while the same mechanism that fixes the target also changes what they do; etc.
- [REV-REPORT] **Report:** every finding with its status (Theoretical / Real / Confirmed, and what confirmed it), and the open items as a list of scenarios with the expected "before → after". This holds for review-only tasks too.
- [REV-MAP] **A map of the change.** The diff is laid out by the spec's items and the user's choice: which files, and roughly how much of the change, serve each item. A part that serves no item is an addition: it goes, or the user decides on it ([HR-SCOPE] in SKILL.md); serialization noise (reordered objects, line endings, etc.) is listed apart. The reviewer compares the map with the diff: a part with no item is a finding. The final report shows the map.
  - Example: "12 files: 4 — item 1 (the popup closes), 5 — connecting to the shared inventory (your choice), 2 — addition: a cache for the price list (not asked, not verified), 1 — serialization noise"; etc.
  - Anti-example: "many files, several related systems touched" as the answer to "why so many?".
- [REV-PREMORTEM] **What the pre-mortem predicted is checked against the diff.** When R&D ran, the brief names the critics' reports on the chosen variant and on the parts it took from other branches ([RND-CRITIC] in [rnd.md](rnd.md)). The report lists each failure they predicted: ruled out with the diff in place (by the diff or by what the project already has, and where), named at the choice as a known limitation (listed, not a finding), or a finding with its status; a finding no critic predicted says so ([RND-POSTMORTEM] in [rnd.md](rnd.md)).
  - Example: a critic predicted that a sync run twice duplicates its records → the diff writes them by a unique key, or the store already rejects a second copy: ruled out; a plain insert into a store that keeps both: a finding; etc.
  - Anti-example: the diff checked against the spec's items only, while a failure the critics predicted ships unguarded.
- [REV-WHO] **After the choice, the reviewer reviews; critics belong to R&D.** Critics break branches before the choice (and in an R&D re-run for a failing part); a change made after the choice goes to the reviewer, once per version ([QA-ROUND] in [qa.md](qa.md)). Test code (drivers, test scenes, helpers, etc.) isn't reviewed as product code: whether its runs count is decided by [PM-ORIGINAL] and [PM-CAN-FAIL] in [play-mode.md](play-mode.md).
- [REV-VERIFY] **Verifiers only where a finding decides something.** A finding that could block or change the fix is pushed to Confirmed by a verifier (a fact agent, [FIND-VERIFY] in [findings.md](findings.md)); the others are listed with their status and the check that would decide them. A verifier per finding is the Deep profile, not the default.
- [REV-BACK] A Real or Confirmed finding that changes the fix sends the work back the same way as a failed QA ([QA-FAILED] in [qa.md](qa.md)), and the new version is reviewed again before QA.
- [REV-OPEN] Open findings go to QA: [REV-REPORT], [REV-CHAIN].
- [REV-CHAIN] **Open findings go to QA together with what to measure.** For each one, the reviewer names the chain from the change to what the player notices, as far as the data shows it: what the change switches off or alters → which states and assets use that → what they visibly do. QA measures along it ([PM-CAN-FAIL] in [play-mode.md](play-mode.md)).
  - Example: a shared table of values changed → which systems read it → which of their results depend on the changed rows → compare those results before → after; etc.
  - Anti-example: "check the other screens", without a word on what in them the change reaches.
