# Depth profiles: Fast, Normal, Deep

Part of the unity-dev skill, read by the main thread (SKILL.md, **Skill files by role**). A profile sets how deep each stage goes: what the agents research, compare and check, and so how long the task takes. It is not the model's reasoning level, and it doesn't change what counts as done.

[PROFILE] **The user picks the profile; the agent never infers it from how big the task looks.**

- **Where it comes from:** a word in the task ("fast", "quickly", "deep", "thoroughly", "a small fix", "no game check", etc., equivalents in any language, see [ACTION-MODE] in SKILL.md), else the project's default in `.ai-profile/project.md` (`profile: fast | normal | deep`), else Fast. A request for speed is Fast, never a reason to skip a stage; a request for a check in the game ("check it in the game", "reproduce it", "with QA", etc.) is Normal; "deep", "thoroughly", etc. is Deep. The agent may say that a run of the game would settle something and name Normal for it; it doesn't switch on its own.
- **Where it shows:** the main thread writes it into the trace header (`"profile"`, [trace.md](trace.md)) and names it in the first answer; every brief names the profile and what it sets for that agent's stage ([BRIEF] in [agents.md](agents.md)), because a sub-agent reads only its own rules.
- **Changed mid-task:** the stages still ahead follow the new profile; the finished ones aren't redone.
- **The same in every profile** (the hard rules and what protects the result): the scope and [SCOPE-TRIGGER]; a spec; the direction sheet ([RND-DIRS]); R&D before implementation and the user's choice; the honest verification level ([HR-VERIFY-LEVEL]); the original chain under check ([PM-ORIGINAL]); "before → after", not a run that reached its end, decides pass / fail ([PM-BEFORE-AFTER]), and only Deep measures the "before" of every situation; the trace. A profile changes the breadth and the loops of a stage, never these. Fast is the one profile with no run of the game: it ends at "implemented, not verified in the game" ([HR-VERIFY-LEVEL]) once the checks of its QA cell pass (in Fast they are the round's acceptance, [AUTONOMY], [QA-FAILED]), with the checks the user runs themselves listed in the report; it never says "fixed".
- Example: "the tooltip shows the old price" (no profile word, no project default) → Fast: a scout, spec, facts, the first idea and a challenger with a critic each, the audience critic and the judge, no stand and no tester, the reviewer by the map of the change, a compile and an Editor data check, the report "implemented, not verified in the game" with "open the shop after a price change and look at the tooltip" for the user; etc.
- Example: "check in the game why the popup doesn't close" → Normal: spec, facts, recipe and tool agents for the mechanics of the popup round, a reproduction of the reported symptoms, every part of their wording, and no other "before", a branch per direction plus one per flagged risk with critique → revise, a review of the diff with Editor checks for open findings, QA of every situation as pass / fail; etc.
- Anti-examples: the agent switches to Normal itself because "this needs a game check" (it names the need, the user picks), or to Deep because the task looks big; a Fast report that says "fixed" or "works"; Fast used to skip the spec or R&D; a Deep task cut short because the stand took long.

[PROFILE-STAGES] **What each profile sets, stage by stage.** It overrides this skill's rules on what a cell sets ([PIPE-PROFILE] in SKILL.md), never what [PROFILE] keeps the same in every profile. A step a cell doesn't name runs as its rule says, so a cell that drops a step says so ("no …", "none", "only …"), and the brief carries those words.

| Stage | Fast (default) | Normal | Deep |
| --- | --- | --- | --- |
| Project profile, scout | in full: cheap, and everything else is blind without them | in full | in full, plus the area's history and similar implementations as their own agents |
| Spec ([SPEC]) | situations: only those the user's words and the task's documents name, the ways into the touched link the scout's table shows ([SCOUT-LINKS]), and what keeps working around them ([SPEC-KEEP]); each item checked as Fast can, in the Editor without Play Mode or on the user's checklist, not as a sweep ([ONE-UNITY]); terms as [SPEC-TERMS] | every situation the words cover | the same, plus a second critic pass after the facts |
| Spec critic ([SPEC-CRITIC]) | one pass; the main thread fixes without a re-check | the critic re-checks until no finding is left | the same |
| Facts ([FACTS-CHAIN]) | every link covered, but links that sit together in code share an agent; with no reproduction a cause is Real at most, marked "by code and logs" ([FIND-STATUS]) | an agent per independent item | the same, plus the history of the area |
| Stand ([STAND-PREP]) | none: no stand is built | recipe agents, then tool agents, for the mechanics of the next round | tools for the mechanics of every spec situation |
| Reproduction ([REPRO]) | none | the reported symptoms, every part of their wording; the tester reports as soon as they are reproduced or refuted, and R&D starts on it. No measured "before" of the other situations: implementation starts right after the choice. For a change to behavior that already exists (a feature, a refactor, etc.) the counterpart is one look at how the touched behavior works now; new behavior has no "now" | the symptoms and the measured "before" of every spec situation, in the setup QA reuses; implementation waits for it; the confirmation in the live game |
| R&D branches ([PIPE-RND]) | the first idea and a challenger, one of them YAGNI ([RND-MINIMAL]); a further branch only where it can change the choice: a direction the branches so far miss ([RND-DIRECTIONS], [DIR-USUAL], [RND-FLAGGED]), a merged core the judge names ([RND-VERDICT]), etc.; sketches ([RND-SKETCH]) | every direction the problem gives ([RND-DIRECTIONS]) as its own branch in the first wave, the YAGNI branch and the challenger among them, plus one per flagged risk ([RND-FLAGGED]); sketches | the same; sketches written out to the paths and files the comparison needs |
| R&D critique | a critic per branch; the branch is brought to the code standard ([RND-STANDARD]); a core flaw gets a revision and its critique again ([RND-LOOP], [RND-VERDICT]) only where the branch, fixed, could be the winner (it would reach the goal and rank first by the judge's ranking, [RND-EFFECT]; a leader with a core flaw is such a branch); the judge's verdict on the critiqued cores, before the critique ends ([RND-VERDICT]), says which; the other branches go to the comparison with what sank them; revisions that do run go in parallel; a further branch or pass only where it can change the choice ([RND-NEXT]); part findings and risks not shown go to the comparison; the judge sees the critics' findings; no deciding run ([RND-DECIDING]): with equal uncertainty, among the branches that reach the goal ([RND-EFFECT]), the variant that changes less wins, or the choice goes to the user, and the missing measurement heads the user's checklist | critique → revise until a round closes no flaw ([RND-STOP]); a merged core the judge names gets a branch in the next round ([RND-VERDICT]) | the same, plus a targeted run for a finding the choice hangs on ([RND-DECIDING]) |
| Review ([PIPE-REVIEW]) | the diff by the map of the change ([REV-MAP]), without the Editor | the diff by the map of the change; the Editor for a finding the data settles ([REV-DATA]) and for open findings | a verifier per finding ([REV-VERIFY]) |
| QA ([PIPE-QA]) | no QA round and no tester: a compile, the asset data read by an Editor script ([FIND-LEVELS] level 2), the changed chain exercised on the original asset in the Editor without Play Mode, for the result of each spec item it touches in that item's situations, not a sweep ([ONE-UNITY]) (a physics query against its colliders, a layout pass of its UI, a method of the original prefab called, etc.), a Unity Test Framework test on the original prefab where the project has a test assembly; the report lists what the user checks in the game, and offers one direct Play Mode check by the main thread | the reproduction scenario again on the same stand: the symptom gone, pass / fail with evidence, repeated after related events ([QA-REPEAT]); the acceptance scenarios of the spec items in the user's words (against what the reproduction or the one look at "now" saw, or the spec's "now"); regressions by the map as pass / fail against "as it was"; no measured before → after values of the other situations: a symptom that is itself a number (a balance, a count, a size, etc.) is measured in its reproduction and again here; invariants ([QA-INVARIANTS]) that can be watched without acting (a value within its bounds, an event that must not happen, etc.), as their source in the project states them, with its conditions (whose action, which states, which exceptions, etc.), watched in the round's logs through every scenario, never inside a measurement the watching would change (a timing, the order of two close events, etc.); no varied sequences; a breach is a FAIL when a spec item states the invariant; it is also a FAIL when the lines the change edits state it, unless the reproduction or the look at "now" already showed it broken; any other breach is a finding with its scenario; the review's open findings as scenarios (a limitation the choice named aside); no breadth (the rest of [QA-SCEN]: a round of its own when the user asks) | before → after values on every situation of every item ([PM-BEFORE-AFTER]), regressions by the map, [QA-REPEAT], the breadth of [QA-SCEN], invariants on varied sequences ([QA-INVARIANTS]) and the confirmation in the live game |

- Numbers and "how many rounds" are not part of a profile: it picks which steps run, how deep their result goes and what a further branch, pass or round needs, not counters.
- Example: in Fast the critics show a core flaw in each branch → the judge first names which branch, fixed, would rank first; that one is revised (both, in parallel, where the judge can't tell them apart) and critiqued again, then the judge; the other goes to the comparison with what sank it ([RND-NEXT]); etc.
- Example: a Fast layout fix → the original screen laid out in the Editor at the reported size, and again after the rotation its item names; the other sizes go to the user's checklist; etc. Anti-example: every edge case and state of the change exercised in the Editor, with the missing systems stood in around the original asset, longer than the change itself.
- Example: a Normal QA → the reproduction scenario, the acceptance scenarios and the regressions run as the QA cell sets them; the review's open findings become scenarios too ([PIPE-REVIEW]); the transitions and the critics' risks wait for a breadth round; etc.
- Anti-example: a Normal QA that skips a spec situation because "the main scenario passed", or a Normal R&D that stops after the first critique because the task looks small.
- Anti-example: a Normal tester leaves out the review's open findings; a Normal round that runs the whole [QA-SCEN] matrix before the report.

[RND-DIRS] **Before the branches start, the main thread writes the direction sheet: what the product's user could get, where what the request came for sits, how that is handled already, what the field does, what keeps working; the branches come from its rows.** Goal: the direction a senior engineer sees first (the link itself, handled the way the project already handles the same situation, or the field's usual way) is in the comparison from the first wave, wherever R&D runs ([RND-WHEN] in [rnd.md](rnd.md)), in every profile; where the product's user could get different results, the directions cover those first, then differ in where the code changes. The sheet is `.ai-profile/work/<task-id>/directions.md`, its rows each with their source (a fact report, the scout's map, a spec item, etc.):
  1. **what the user gets:** where the task has a product's user, the different results they could get in the spec's situations, each as what they would see or do (the same result reached in another layer of the code is not another one), from the spec's goal and items ([SPEC-FORMAT] in [spec.md](spec.md));
  2. **the link:** the place in the chain where what the request came for sits (a bug's cause with the condition that goes wrong there; a cost; a duplication a refactor removes; for new behaviour, the link the project uses for this kind of thing; etc.), from the fact that shows it ([HR-EVIDENCE] in SKILL.md), not from the first finding near it; where the map and the facts name two places, both go in, with which one it is;
  3. **the analogue:** how that link, or the project, already handles the same situation for other objects or cases ([DIR-EXISTING], [RND-EXISTING] in [directions.md](directions.md)), from the scout's links table ([SCOUT-LINKS] in [scout.md](scout.md)) or a fact report;
  4. **the usual ways:** the field's usual techniques for this class, each by the level it acts at ([DIR-USUAL]), and an unusual one where it is worth a look;
  5. **kept:** the kept items of the spec, by number ([SPEC-KEEP] in [spec.md](spec.md));
  6. **taken:** the directions that become branches, each by its principle with the row it comes from (the first idea, YAGNI, the challenger, the analogue, a technique, etc.) and the result for the user it gives, and the rows not taken, with why in a line ([DIR-USUAL]).
  A row no report answers is a fact item for a fact agent ([PIPE-FACTS] in SKILL.md), not the main thread's own reading ([MAIN-WAITS] in [agents.md](agents.md)); until it returns the row says "not yet known: <agent>", a branch for that row starts when the agent returns ([RND-FLAGGED]), and "none" is written only with the search that showed it. The sheet comes before the branches, not as their summary. The R&D stage node carries the rows as `attrs` (`user`, `link`, `analogue`, `usual`, `kept`, `taken`), the sheet's path in `ev` and `RND-DIRS` in `r` ([trace-agent.md](trace-agent.md)); every brief of the stage names the sheet, and a branch gets its user, link, analogue, usual and kept rows and its own line of the taken row, not the other directions ([RND-ISOLATE] in [rnd.md](rnd.md)); the judge scores every core against the user, link, analogue, usual and kept rows ([RND-BAR] in [verdict.md](verdict.md)). Challenge questions: does every result of the user row have a direction that gives it? → a branch for it (in Fast, the further branch its cell allows), or why not in the user's terms; that it doesn't move a technical measure (a count, a cost, etc.) or sits in another layer isn't a reason by itself. Does the analogue row name a place in this project, or only "none"? → a fact item, or the search already in the scout's map or a report. Does a technique of the usual row act at the link, and does a branch use it there? → a branch for it, or its reason in the taken row. Is the first branch of the taken row the first idea only because it came first? → the analogue or the usual way gets a branch of the first wave next to the first idea ([DIR-USUAL]; in Fast, the further branch its cell allows).
  - Example: "checkout is slow" → the user row: the buyer doesn't wait at the pay step (answered at once, the payment confirmed in the background); fewer steps; the page usable while it loads; then the link and the layers for each; etc.
  - Anti-example: the directions differ only by layer (the database, a cache, the network), and "answer at once, confirm in the background" is left out because it doesn't lower the server's time.
  - Example: "the export drops the last row" → link: the writer's loop ends a row early at a page break; analogue: the importer walks the same break with a page-aware iterator; usual: an iterator that closes the page (the loop), a count check after the loop (the caller); kept: items 2–3 (every row of the other exports still comes out); taken: the analogue's iterator (from what exists), the count check (the first idea, YAGNI), a challenger rejecting "the page break is the only break"; etc.
  - Anti-example: the branches are the first idea and its opposite, no row says how the project already does it, and the analogue never gets a branch; or the sheet written after the branches returned, as their summary.

[RND-NEXT] **R&D's next round comes from what the critique shows, within the profile's budget.** The rounds end by [RND-STOP]: Normal and Deep revise until then, as their cells say; Fast runs only the rounds its cells allow. With no candidate left at the stop, the comparison of every variant tried goes to the user: "not done: needs your choice". Within that, the main thread decides each round from the critics' findings and the judge's verdict, and the brief carries the cell. Ask: is a flaw fixable inside its direction? → a revision ([RND-LOOP]); if not, a new direction. Would a merged core close what neither core closes alone? → that core as a branch ([RND-VERDICT]). Is a direction missing ([RND-DIRECTIONS], [DIR-USUAL], [RND-FLAGGED])? → a branch for it. In Fast, can that round change the choice, a revision included (the judge's verdict says which branch, fixed, could win)? If not, it doesn't run.

- Example: a cache branch is fast but serves stale prices after an edit, an invalidation branch stays fresh but slow on a cold start, and each core holds the other's fix → a merged core next round, in Fast too; etc.
- Example: what the critique left changes no winner (a risk not shown, a part to drop, a style remark, etc.) → the comparison, no round, in any profile; etc.
- Anti-example: a cell read as a count ("one pass, no revision"), so a flaw a short revision closes sinks a direction that, fixed, could win, and a branch that stops what the system did wins as the smaller change; or Fast rounds that go on after the winner is clear, a revision of a branch that couldn't win among them.
