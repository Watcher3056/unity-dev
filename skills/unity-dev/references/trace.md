# Trace: the main thread's part (hard rule)

Part of the unity-dev skill, read by the main thread together with [trace-agent.md](trace-agent.md), which holds the fields and the rules every agent follows.

- **Where.** The main thread picks `<task-id>` at stage 0 (the date and a short slug) and writes `main.jsonl`, starting with `{"task":"<short title in the user's language>","skill":"unity-dev","profile":"fast|normal|deep"}` ([PROFILE] in [profiles.md](profiles.md)). Create the trace for the mode question before confirmation without a `"profile"` value. After the answer or an explicit switch, append an updated header as a new line with the same `"task"` and the confirmed `"profile"`; keep earlier headers so finished stages retain their mode ([PROFILE]).

**Fields only the main thread writes:**

| Field | Meaning |
| --- | --- |
| `k` | `par`: the children run in parallel; `sel`: the children are alternatives and one wins; omitted: the children are steps in order |
| `sg` | on a stage node: the stage's tag from **Pipeline** (`PIPE-SCOUT`, `PIPE-REVIEW`, etc.), not its number; the viewer takes the number, the order and the name from the skill |
| `by` | who said or decided it: `user` on a node of the user's input; on a choice, `user` or `agent` ([TRACE-USER]) |
| `go`, `why` | on a problem the task found: what the main thread decided about it (`fix`, `check`, `leave` or `ask`) and why, in plain words ([TRACE-GO]) |

- [TRACE-SEL] **Under a choice (`"k":"sel"`), the children are the alternatives.** The viewer draws every child of a `sel` node as one more way to go, so a step about one alternative (its critic, its revision, its measurement, etc.) goes under that alternative (`p`), and a step that weighs them all (the judge, the audience critic) lists what it weighed in `in`: the viewer draws it after the alternatives, with the arrows from them.
  - Example: two ways to keep a shop's prices fresh → `{"id":"rnd","sg":"PIPE-RND","t":"Price refresh compared","st":"run","k":"sel"}`, the alternatives `{"id":"v-cache","p":"rnd","t":"A: cache the price list","st":"run"}` and `{"id":"v-push","p":"rnd","t":"B: push each price change","st":"run"}`, A's critic `{"id":"crit-cache","p":"v-cache","t":"Risks of A","st":"run"}`, and the judge `{"id":"judge","p":"rnd","t":"A and B weighed","st":"run","in":["v-cache","v-push","crit-cache","crit-push"]}`; etc.
  - Anti-example: `{"id":"crit-cache","p":"rnd","t":"Risks of A","st":"run"}`: under the choice with no link to A, the graph shows the critic as a third way to refresh the prices.
- [TRACE-FORM] **A form the verdict composes is a node of its own, made from the nodes it came from.** When the judge's verdict takes a winner's core with a part from another branch, or names a merged core for the next round ([RND-VERDICT] in [rnd.md](rnd.md)), the main thread adds a node for that form as one more alternative under the choice (`p` = the `sel` node, next to the branches), a new solution on the graph with `in` listing the branch nodes it was made from and `u` saying what came from where; the choice and the implementation point to this node, not to a branch alone. A form taken as is from one branch needs no node: the branch is the form.
  - Example: the verdict "B's core with A's event debounce" → `{"id":"form-b","p":"rnd","t":"B with A's debounce","st":"ok","in":["v-push","v-cache"],"u":"Push each change, debounced the way A did; the price list isn't cached"}`, then `{"id":"impl","sg":"PIPE-IMPL","t":"Implement the chosen form","st":"run","in":["form-b"]}`; a merged core sent to the next round is the same node with `"st":"run"` and its own critic under it; etc.
  - A core changed by a revision needs no form node of its own, but its history: the node of the branch's last revision says in `u` what the revision added, what it dropped and from where (another branch, its critic's finding, etc.), so the card reads as a history, not as a new variant. Example: `{"id":"v-cache-r2","p":"v-cache","in":["crit-cache"],"st":"ok","u":"Added invalidation on write from the critic's finding; dropped the TTL"}`; etc.
  - Anti-example: the implementation node points at B, and the graph never shows where the debounce came from.
- [TRACE-FOLLOWUP] **A follow-up from the user continues the same trace.** When the user's question or answer starts pipeline work (R&D, a fix, a new check, etc.), the main thread opens that stage's node before spawning its agents, as for any stage. When that message comes after the task's answer, once the work had ended (feedback on the result, a new request about it, etc.), the main thread first writes the message as a node of its own with `"by":"user"` and no `p` ([TRACE-USER]): `t` says it briefly in the user's words, `s` what it changes for the work, `ev` the files and pictures they gave. The stages it starts are new nodes (new ids) that take it in `in`; the earlier stages keep their nodes as they ended. The viewer starts a new iteration of the task from that node, and the earlier iterations stay as they ended, each with its own outcome.
  - Examples: after a reproduction the user asks which fix is best → the main thread writes the R&D stage node with `"st":"run"`, then spawns the branches; after the answer the user writes "the export still drops the last row" → `{"id":"you-lastrow","t":"The export still drops the last row","s":"the fix is checked again on a file whose rows end at a page break","st":"ok","by":"user"}`, then `{"id":"facts-2","sg":"PIPE-FACTS","t":"Facts: the last row","st":"run","in":["you-lastrow"]}`; etc.
  - Anti-examples: treating the question as a plain answer, running R&D agents, and leaving the R&D stage off the graph; the feedback after the answer written under the last stage (`"p":"qa"`), so the viewer can't tell where the new iteration starts; the earlier QA stage reopened with `"st":"run"` for the new check, so the earlier iteration loses its result.
- [TRACE-NEXT] **A closed stage and the next step go in one append.** When a stage ends (a review with findings, a QA round, a choice, etc.), the line that closes it and the line that opens what follows (the fixes, the next round, the next stage, etc.) are written together, before the work of the next step starts: the graph then shows the current step from its first moment, not after it has ended. A stage that stays open while later stages run (the reproduction's "before" measurement during R&D, etc.) says in `s` what still runs in it, and closes when that part ends.
  - Example: the review finds two fixes → one append: the review stage with `"st":"fail"` and its result, and `{"id":"fix-2","sg":"PIPE-IMPL","t":"Fixes, round 2","st":"run"}`; etc.
  - Anti-example: the fix round written after it ended, opened and closed in one line, so the graph showed nothing while it ran.
- [TRACE-REUSE] **A new assignment to a sub-agent that already worked names its trace again.** When the main thread hands an agent from an earlier step a new task (a follow-up message, a reused tester, etc.), the brief names the trace folder and the id of the node opened for this assignment, as for a new spawn; otherwise the agent keeps writing into the trace of its earlier task, and that task looks alive again.
- [TRACE-ANSWER] **An answer closes its question at once.** When the user answers a question (through the question card, in a chat message, etc.), the main thread writes the answer into that question's node (`ans`) and updates its `st` before going on. The work the answer starts takes the question's node in `in`, so the graph shows that it follows from the answer; the answer itself stays only in the question's `ans`. A question that changes before its answer keeps its node: a line with the same `id` brings the new `q` and `o`, and the card is asked again (user-output.md, rule 11).
  - Example: the user picks variant B in the menu → `{"id":"fix-choice","q":"Which fix?","o":["A","B"],"ans":"B","st":"ok"}`, then `{"id":"impl","sg":"PIPE-IMPL","t":"Implement B","st":"run","in":["fix-choice"]}`; etc.
  - Anti-example: the work node gets its own `"ans":"the user chose B"` and no `in`, so on the graph it hangs off its stage with no link to the question it answers.
- [TRACE-USER] **What the user says that steers the work is a node of its own, with `"by":"user"`:** the scope they set, a constraint, a correction mid-task, the permission to pick, a file or a picture they gave, etc. `t` says it briefly in their words, `s` what it changes for the work, `ev` the paths of the files and pictures they gave. It goes under the stage under way (`p`), or with no `p` when it came with the task or after the task's answer ([TRACE-FOLLOWUP]). Each step that takes it into account lists it in `in`, so the viewer draws the user's input coming into the steps it shaped. An answer to a question stays in the question's node ([TRACE-ANSWER]), not in a node of its own. A choice says who made it: its node (the choice stage, or the question it answers) gets `"by":"user"` when the user picked and `"by":"agent"` when the agent did (the user said to pick and do it, [RND-GATE] in rnd.md).
  - Examples: the user writes "don't touch the price table, the designers own it" → `{"id":"you-prices","p":"facts","t":"Price table stays as it is","s":"the designers own it: the fix goes elsewhere","st":"ok","by":"user"}`, and the R&D branches take it: `"in":["cause","you-prices"]`; the user gives a recording of the bug by its path → `"ev":["Docs/bugs/menu-flicker.mp4"]` on their node; the user says "choose yourself" → their node `you-pick`, and the choice stage `{"id":"choice","sg":"PIPE-CHOICE","t":"Choice","st":"skip","s":"the user: pick and implement; B picked","by":"agent","in":["you-pick"]}`; etc.
  - Anti-example: the constraint goes only into the briefs, so the graph shows the branches but not that the user narrowed them.
- [TRACE-GO] **Every problem the task found gets the main thread's decision, on the problem's own node.** `go` says what happens to it: `fix` (fixed in this task), `check` (checked further first: a measurement, a scenario in the game, etc.), `leave` (not touched in this task: outside the requested scenario, an old bug, a risk accepted; it goes to the report's "found, not touched" list, [HR-SCOPE] in SKILL.md) or `ask` (the user decides: a change of behavior outside the scenario, [SCOPE-TRIGGER] in SKILL.md). `why` gives the reason in plain words ([TRACE-PLAIN] in trace-agent.md) when the problem alone doesn't make it plain. The main thread writes them as it decides, in the append that closes the stage that found the problem ([TRACE-NEXT]); a later line changes them when the decision changes (a `check` that confirmed the problem, now `fix`, etc.). Where the problem went is the `in` of the steps that take it (R&D, the implementation, a QA scenario): the viewer shows each problem, the decision on it, where it went and how that ended as one line of the task, so the user sees what became of everything that was found.
  - Examples: the reported bug, confirmed → `{"id":"buy2","go":"fix"}`; a shared screen the change may hurt → `{"id":"filter-y","go":"check","why":"The tester opens screen Y in the game before the task is called done"}` and the QA scenario takes it: `"in":["filter-y"]`; an old export bug found on the way → `{"id":"export-stale","go":"leave","why":"Outside this task: listed in the report for you"}`; a fix that would change how old saves load → `{"id":"save-migrate","go":"ask","why":"Old saves would load differently: your call"}`; etc.
  - Anti-example: the stage's `s` says "3 problems: fixing 1, the rest later", and no problem has `go`, so the user sees three problems and no decision on any of them.
- [TRACE-CHECK] **Check the trace before every answer to the user**, not only before "done", and before writing the answer, so the answer is the last message; upkeep of the trace never gets a message of its own: `main.jsonl` has a node for each stage that ran and each sub-agent spawned since the previous answer; the sub-agents' lines use the trace fields; no step that has ended is still `run`, no answered question still waits, every stage that ended and the choice say in `uh` and `u` what they came to ([TRACE-PLAIN] in trace-agent.md), and every problem found so far has its `go` ([TRACE-GO]). Add what's missing.
- [TRACE-SKIP] **A stage that doesn't run is still on the graph:** a stage node with `"st":"skip"` and the reason in `s`. Only the agent knows why a stage was skipped; without the node the user sees a gap in the stage numbers and can't tell a reason the skill allows from a missed step.
  - Examples: `{"id":"rnd","sg":"PIPE-RND","t":"R&D","st":"skip","s":"approach fixed by the user: reuse the existing cache"}`; the user said to pick the variant yourself → `{"id":"choice","sg":"PIPE-CHOICE","t":"Choice","st":"skip","s":"the user: pick and implement"}`; etc.
  - Anti-example: the trace goes from the facts straight to the review, with no node for the stages between them.
- **The viewer checks** these citations in every finished stage and flags the ones no node in it has. A citation that names profiles is expected only when the `profile` from the last header before that stage began is one of them ([PROFILE-STAGES] in [profiles.md](profiles.md)); a missing or unknown starting profile checks that stage against every citation. Old traces without mode history use their header value:

| Stage | Expected citations |
| --- | --- |
| `PIPE-FACTS` | `SPEC`, `SPEC-CRITIC` |
| `PIPE-RND` | `RND-DIRS`, `RND-FIRST-IDEA`, `RND-CHALLENGER`, `RND-CRITIC` per branch, `RND-JUDGE`, `RND-BAR`, `RND-STOP` (Normal, Deep) |
| `PIPE-CHOICE` | `RND-SHOW-ALL`, `RND-GATE`, `CHOICE-ITEMS` |
| `PIPE-REVIEW` | `REV-REPORT`, `REV-MAP` |
| `PIPE-QA` | `QA-SCEN` (Normal, Deep), `PM-BEFORE-AFTER` (Normal, Deep), `QA-ROUND` (Normal, Deep) |

## Before you say "done"

- Did I change only what was asked, and can I justify every addition? Does the report show the map of the change ([REV-MAP]) and go item by item through the spec ([SPEC-REFS])?
- Did I go through the relevant challenge questions (directions.md, findings.md) instead of applying a default?
- Are temporary diagnostics kept out of the commit, and are the test setups listed for the user? Are the changes in the branch the user expects?
- Did I run R&D and wait for the user's choice before implementing? Did I record what I learned in `.ai-profile/knowledge.md`?
- Does the trace show every stage with its final status?
- Does the answer start with the result and show it visually (user-output.md)?
