# Trace: writing your nodes (hard rule)

Part of the unity-dev skill, read by every role (SKILL.md, **Skill files by role**); the main thread's own part is [trace.md](trace.md).

The user follows the task live in a viewer: a tree of stages, hypotheses, branches, checks and choices, with the rules and evidence behind each step. The trace is the viewer's only source for that tree, so every task that runs the pipeline keeps one. It stays short: the viewer itself shows the rule texts, the evidence and the agents' timing.

- **Where.** `.ai-profile/trace/<task-id>/` in the project. The main thread writes `main.jsonl`; each sub-agent appends to its own `<its task name>.jsonl` in the same folder, under the node the main thread opened for it (its brief names the folder and that node's id). This file is not a project change, so read-only agents write it too. If the sandbox can't write files, skip the trace and say so in one line. The folder holds the trace files and the images and videos they point to; other working files (bridge outputs, logs, dumps, scripts, etc.) go to `.ai-profile/work/<task-id>/`.
- **One JSON line per node:** a stage, a hypothesis, an R&D branch, a check, a finding, a QA scenario, the user's choice, etc. A later line with the same `id` updates that node: it replaces `t`, `s`, `u`, `st`, `f`, `q`, `o`, `ans`, `now`, `pro`, `con` and `attrs`, and adds to the lists (`r`, `ev`, `in`, `n`, `x`, `plan`, `done`, `skip`).
  - Example: `{"id":"b","p":"rnd","t":"B: unsubscribe on close","s":"judge 8, chosen","st":"ok","in":["h1-res","repro-res"],"r":["RND-JUDGE"],"ev":["Assets/UI/PopupView.cs:88"]}`

| Field | Meaning |
| --- | --- |
| `id` | unique within the task |
| `p` | the parent node; a stage has none |
| `t`, `s` | title and result, a few words each, in the language the task came in ([TRACE-LANG]) |
| `u` | the same in plain words for the user, one or two sentences, on the nodes the user follows the task by ([TRACE-PLAIN]) |
| `uh` | what the step came to, in a few plain words: the headline the user reads first, on the nodes that get `u` ([TRACE-PLAIN]) |
| `st` | `run`, `ok`, `fail`, `drop` (refuted or rejected), `wait` (waits for the user), `skip` |
| `in` | the nodes whose results this one uses: confirmed facts into R&D, the chosen branch into implementation, a failed scenario into the next round, etc. A refuted or rejected node feeds nothing |
| `r` | IDs of the rules that decided this step, as tagged in this skill and its references, e.g. RND-STOP |
| `ev` | evidence pointers: `path:line`, `path:from-to`, `commit:<hash>`, the path of a screenshot or a video ([TRACE-MEDIA]), etc.; never pasted content |
| `n`, `x` | optional: a nuance found; why it was rejected, or the alternatives |
| `pro`, `con` | on a variant compared with others (an R&D branch, etc.): what speaks for it and what against it, one short point per item ([RND-PROS] in verdict.md) |
| `attrs` | facts by name, shown as a table on the card and side by side across variants: on a variant, the bar's rows written by the judge in one line with its `pro` and `con` (`user` and `effect`, the two cells of the effect row, `kept`, `place`, `way`, `guards`, `footprint`, `risk`, `shown`, and a key per applicable criterion, each a short string that starts with ✅, ❌ or ⚠️ and names what shows it; [RND-BAR] in verdict.md); on the R&D stage node, the direction sheet's rows (`user`, `link`, `analogue`, `usual`, `kept`, `taken`; [RND-DIRS] in profiles.md). Replaced whole on update |
| `tags` | on a variant: the tags the comparison earned it (user-output.md): `Recommended` on one variant only; `Safe`, `Minimal`, `Strong`, `By the book`, `Easy to verify` wherever earned, repeatable across variants, none on a tie; the viewer shows them beside the variant's name |
| `f` | on a node that records a problem the task found (a cause, a defect, a risk, a regression, something found and not touched, etc.): its status by [FIND-STATUS], `theoretical`, `real` or `confirmed` |
| `ft`, `fs` | with `f`: what the problem is and how bad it is for the player or the user. `ft`: `bug` (works wrong now: the reported problem, or one found on the way), `regression` (broken by this task's change), `risk` (not seen broken, can break: a shared consumer, an edge case, a fragile order, etc.). `fs`: `critical` (a crash, a hang, lost progress or saves, wrong money or purchases, a core mechanic unusable, etc.), `major` (a feature visibly works wrong, a rule of the game breaks, with a way around), `minor` (cosmetic, rare, seen only in logs or the editor, etc.) |
| `q`, `o`, `ans` | when the node answers a question: the question (a menu to the user, a sub-agent's question, the R&D question, etc.), the options offered, and the answer: the user's pick or the agent's conclusion. A node that waits for the user has `q` and `o`, no `ans` yet |
| `plan`, `now`, `done`, `skip` | on a step that takes a while (a Play Mode round, a wave of sub-agents, an R&D loop, etc.): its plan items, the item in progress, the finished ones and the dropped ones. When the work turns out bigger, a later line adds the new items to `plan`; the viewer marks them as added |

- [TRACE-FIELDS] **Only these field names and these `st`, `f`, `ft` and `fs` values.** The viewer reads nothing else, so a result under another name stays hidden and another status gets no colour.
  - Example: a finding with its evidence → `{"id":"f2","p":"facts","t":"Handler removed on re-open","s":"confirmed in Play Mode","st":"ok","ev":["Logs/run.log:41-58"]}`.
  - Anti-examples: `{"id":"f2","fact":"…","evidence":[…]}` (no `t`, `s` or `ev`: the node shows only its id); `"st":"complete"` or `"st":"open"`; a field of your own such as `risk` instead of `n`.
- [TRACE-LANG] **The trace and the agents' own text are in the language the task came in.** The user reads both in the viewer: the header's `task`, the nodes' `t`, `s`, `n`, `x`, `q` and `o`, and what each agent says (its notes and its final report). The language is the one the user wrote the task in, and the header's `task` shows it to every agent; a brief, a reference or code in another language doesn't change it. Code names, paths, log lines and quotes stay as they are.
  - Example: the user writes the task in German and the main thread briefs a sub-agent in English → the sub-agent's node is `{"id":"price","p":"facts","t":"Preis wird doppelt abgezogen","s":"zweiter Klick vor der Serverantwort","st":"ok","f":"real"}`, and its report is in German too.
  - Anti-example: a sub-agent briefed in English writes `"t":"Price deducted twice"` and reports in English, so the user's graph and agent cards mix two languages.
- [TRACE-FIND] **A problem the task found is a node with `f`.** The viewer lists these nodes as the task's problems, with their status and their place on the graph; a problem said only in a stage's `s` or in prose doesn't reach that list. `st` still says how the step went: a review that found a defect finished `ok`. The list is for the user: the node's `t` names what goes wrong as the player or the user notices it, in their words, and `s` gives the cause in the code, where code names fit. `s` says what was found, not where the work goes next: who checks it further is in the graph (`in`) and in the briefs. With `f` go `ft` and `fs`: the list puts the worst first and shows a risk apart from a bug; whoever learns more updates them with a line of the node's `id`.
  - Examples: a review finding → `{"id":"r2","p":"review","t":"Shared filter also hides screen Y","s":"Y loses its list after the change","st":"ok","f":"real","ft":"regression","fs":"major","ev":["Assets/UI/Filter.cs:40"]}`; a fact → `{"id":"buy2","p":"facts","t":"A purchase takes the price twice","s":"a second click before the server answers; Cart.Buy doesn't lock the button","st":"ok","f":"real","ft":"bug","fs":"critical","ev":["Assets/Shop/Cart.cs:88"]}`; a shared consumer the change may hurt, not seen broken → `"f":"theoretical","ft":"risk","fs":"major"`; the cause confirmed in Play Mode → `"f":"confirmed"` on the fact that shows it; an old bug found and not touched → its own node with `f`; etc.
  - Anti-examples: the stage's result "3 issues found" with no node per issue; the status written into `s` (`"s":"Real"`) or a finding marked `"st":"fail"`, so it reads as a failed step; `f` on a check that found nothing or on a refuted hypothesis; `"t":"Cart.Buy has no guard"` (the code, not what goes wrong); `"s":"handed to the tester"` (the next step, not the finding).
- [TRACE-SAME] **A problem already on the graph keeps its node.** Whoever checks it further writes a line with its `id`: the new `f`, `s` and `ev`; a check that is a node of its own takes it in `in`. A second node for the same problem puts it in the user's list twice, and its two statuses disagree. Your brief names the nodes of the problems you check; one you find on the graph yourself counts the same.
  - Example: the scout notes `{"id":"buy2","p":"scout","t":"A purchase may take the price twice","s":"Cart.Buy doesn't lock the button","st":"ok","f":"theoretical"}`; the facts agent reproduces it → `{"id":"buy2","s":"two clicks within 200 ms charge twice","f":"confirmed","ev":["Logs/shop.log:40-52"]}`; or its reproduction is a node of its own → `{"id":"buy2-repro","p":"facts","t":"Double charge reproduced","st":"ok","in":["buy2"]}` and the line updating `buy2`; etc.
  - Anti-example: the facts agent writes `{"id":"charge-twice","p":"facts","t":"Purchase charges twice",...}` next to the scout's `buy2`, so the list shows one problem as two.
- [TRACE-EVIDENCE] **Evidence shows the subject itself, so that the user sees the result at one look.** Goal: the user recognizes the thing on the evidence (a behavior, a state, an artifact of the product) and sees the result where it happens, without the report.
  - [TRACE-SHOW] **When: where evidence says more than the words, the step makes it.** The user follows the task by its key moments, and some of them are seen faster than read: a problem in an asset, a scene or a UI; a new or changed prefab, scene, UI or material; a before and after in the game; measured values before and after. These get it: the asset with the problem's object highlighted, its preview before and after the change, the game before and after, a chart of the values. A change of code alone, or a step with nothing to see, gets none.
  - **Direction.** Show the user the product's own picture: a recording of what happens, a picture of a state. Where a drawing explains it faster (where things are, how they move), it is drawn in the subject's own space (the scene, the screen, the page, etc.), animated where things move; a chart only for numbers with no place in it (frame time, memory, etc.); before and after side by side stays welcome.
    - Examples: vehicles in a convoy bunch up → a top view of the road with the vehicles moving over time, the gaps labeled; a load time improved → two bars «4.1 s → 1.3 s»; etc.
    - Anti-examples: the gap between two vehicles plotted as a line over frames, with no picture of where they are; a still top view of something whose point is how it moves.
  - **Every piece of evidence reads on its own:** the title is the question in the user's words; one line is the answer; labels in the product's words, not variant codes or engine measures; the comparison is "now → expected" or "before → after"; the internal variants stay with the engineer's node (an R&D branch, a measurement, etc.). The deliverable is shown the same way: a level built → a fly-through and pictures of its key spots; a component → its render; an API change → the request and the response before and after; a migration → the two records side by side; etc.
  - **How.** A recording comes from the project's own recording means where it has one (a recorder package, etc.), else from frames saved during the run and composed into a clip (Python, ffmpeg, etc.); a picture of an asset from the skill's `scripts/AssetShot.cs`, which renders it in a preview scene, so nothing in the project or the open scene changes, and paints and frames a given object of it (an invisible one, such as a collider: the frame alone), the tool going into an Editor folder of the project's test folder and staying there ([PM-SETUP-STAYS] in play-mode.md); a frame of the game from the bridge's screenshot in Play Mode, when the user chose the window ([PM-WINDOW] in editor.md), these two only by the role that holds Unity, a role without it asks that role ([FIND-LEVEL] in findings.md); a chart from the measured values, with matplotlib; drawings and compositions from the positions and frames the run already records (PIL, matplotlib, etc.). **A recording keeps the native frame rate and the native pixels: no upscaling;** a crop only inside a composition, not instead of the whole frame. Frames polled from outside by the step of a scenario give the caller's rate, not the product's: fine for a state, not for motion.
    - Example: a recorder, a device's or a browser's own screen recording, a terminal session recording, rather than a screenshot after every step of the automation; etc.
    - Anti-example: a crop of a small region upscaled, composed at a few frames per second from screenshots taken per step.
  - **Pipeline.** Goal: no gap between the demo capture and what the product renders for its user. Capture through the product's own output pipeline, in a run of the game always ([QA-EVIDENCE] in qa.md); the viewpoint, the moment and the framing change to suit the demonstration; elsewhere the pipeline changes only where the demonstration needs it (a highlight, a debug view, etc.), with the change named on the evidence. Question: would the user's screen show it like this, and if not, does the evidence say what was changed?
    - Example: the product's own screen or camera turned to where the subject is; an invisible collider framed in the asset's render (`AssetShot`); etc.
    - Anti-example: an output the stand added for the capture, with its own settings, shown as the product's picture.
  - [TRACE-MEDIA] **Where: in the step's own `ev`.** The viewer shows a picture on the step's card and plays a video in place (`.png`, `.jpg`, `.gif`, `.webp`, `.mp4`, `.webm`, `.mov`), so the user sees it without opening files; one only described in `s`, or kept for the final answer, doesn't reach the graph. A file made for the trace goes into the trace folder, one made elsewhere stays where it is; `ev` gives its path from the project's root. A before and after are a pair, `<name>-before.<ext>` and `<name>-after.<ext>` (`.mp4` for a recording, `.png` for a picture), both in the node's `ev`; the node's `u` or `s` says what the picture shows. Open it before claiming anything about it, and say what it is: a recording, a render, a frame of the game, a chart (user-output.md).
  - Examples: a car drifts on a straight road → a recording "steering straight → 3 m off the lane", and a top-down of the track with its path, animated, only where the whole path matters; a form loses its input → a recording of typing, then the reload; a layout shift → two pictures side by side in the same crop; a job reorders records → the two outputs side by side with the differing lines marked; a load time improved → two bars "4.1 s → 1.3 s"; a wrong total → the table rows that sum, with the wrong one marked; a door's trigger a meter off the doorway → the prefab with the trigger framed, in the problem's `ev`; a check of a UI fix → `{"id":"qa1-list","p":"qa1","t":"List keeps its scroll after a refresh","s":"the same row on top before and after","st":"ok","ev":[".ai-profile/trace/<task-id>/list-after.png"]}`; etc.
  - Anti-examples: bars "variant A / B / C" where a recording of the product would show it; a drawn diagram of what the capture already shows; a frame from the middle of an animation as proof that it plays; a long recording of a static screen; a title made of the capture conditions; a picture of raw data; `"s":"the screenshot shows the button in place"` with no path; the picture a scenario's question needs cited only by the round's node at the end, so that scenario's card has none; a picture at every step, all of them alike; a picture of a code change; a highlight made by changing the prefab's own material and saving it.
  - Challenge questions: can it be captured? Does seeing it need time? What would the user understand at one look?
- [TRACE-PLAIN] **What the user follows the task by says it in plain words: `u`.** In the viewer's Result the user reads the task as a chain of answers, not as the graph: what goes wrong and why, which ways out were weighed and what each does, what was chosen and why, what changed, whether it works. `t` and `s` are pointers for the graph; `u` is that answer: one or two sentences in the task's language ([TRACE-LANG]), in the words of the game or the product the user knows, with no code names, rule tags or file names, and a number only with what it means. These nodes get it, from whoever writes them: a stage when it ends (the main thread: what the stage came to); a problem the task found ([TRACE-FIND]: why it goes wrong, as the player would understand it); an R&D branch (the branch: what this way does, and how); the choice (the main thread: what was taken and why); a check that failed (what the player would see). A later line changes `u` only when the answer itself changed: new measurements go to `s`, `n` and `ev`. Each of these nodes also gets `uh`: what it came to in a few plain words, the headline the viewer shows above the details (a moment's header, the task's line, a variant's line), which `u` then explains. The headline carries what decides it: a variant not taken, a fix not yet confirmed, etc.
  - Examples: a problem → `"u":"A quick double tap on Buy charges twice: the button stays active until the server answers"`; a branch → `"u":"The popup listens for the purchase each time it opens, so a second purchase closes it the same way as the first"`; the choice → `"u":"We take B: it removes the cause, and the three other popups that listen the same way get fixed too; A would only hide it in the shop"`; the QA stage → `"u":"Two purchases in a row now close the popup and the price stays still. Not checked: a purchase while offline"`; etc.
  - Headlines: a stage → `"uh":"Two purchases in a row now close the popup","u":"The popup listens again each time it opens. Not checked: a purchase while offline"`; a round that didn't work → `"uh":"First fix not taken: the popup still sticks after a refund"`; a problem → `"uh":"A double tap on Buy charges twice"`; etc.
  - Anti-examples: `"uh":"Implementation"` or `"uh":"QA round 2"` (the step's name: that is `t`); `"uh":"First fix restores the popup"` while `u` goes on "it is not taken" (the headline drops what decides it); `"u":"Null check in OnPurchase, return early"` (the code, not what it does); `"u":"FPS 41 → 58"` (a number with no meaning: "the menu scrolls smoothly now: 58 frames a second instead of 41"); a problem's `u` overwritten with the numbers of a later check, so the user loses why it went wrong.
- **Pointers, not prose.** Write IDs and pointers; add `n` and `x` only when they say what the pointers don't.
- **Cite honestly.** `r` lists the rules actually followed at this step. Never cite a rule you skipped: a skipped rule shows up as missing, and that is what the user needs to see.
- [TRACE-NOW] **When: the current action is always on the graph.** A node with `"st":"run"` goes in as soon as a step starts: a stage; each sub-agent the main thread spawns (the main thread writes it at spawn time and passes its id in the brief); the main thread's own steps (the implementation, a measurement before the change, etc.). When the step ends, a line with the same `id` updates it, and its child nodes go in one append. A sub-agent appends each of its nodes as soon as that step of its work ends (a finding, a refuted hypothesis, a check, etc.), under the node opened for it; when the step is an item of its plan, the item's nodes and the line that marks it done go in one append (see TRACE-PLAN). Its last line updates that node's `s` and `st`. Append UTF-8 text with whatever the shell offers. The main thread writes the lines of one step in one append (a stage and the sub-agents it spawns go together), and doesn't write a sub-agent's progress for it.
  - Example: the main thread spawns the tester for a measurement before the change → it writes `{"id":"before","p":"impl","t":"Before measurement","st":"run"}` at once; the tester appends each scenario node with `"p":"before"` as that scenario ends, and before it returns the line `{"id":"before","s":"bug reproduced in 3 of 3","st":"ok"}`; a sub-agent checking three screens of a UI appends, after the first one, the node `{"id":"inv-scroll","p":"ui-check","t":"Inventory list loses its scroll","s":"reset on every refresh","st":"ok","f":"real","ev":["Assets/UI/InventoryView.cs:57"]}` and `{"id":"ui-check","done":["Inventory"],"now":"Shop"}` together; etc.
  - Anti-examples: a sub-agent works for half an hour and the graph shows nothing new until it returns; the nodes of all three screens appended together when the agent returns, so the branch stays empty for twenty minutes and then fills at once.
- [TRACE-PLAN] **A step that takes a while shows its plan and its progress.** As it starts, its node gets `plan`; after each item, one append: the nodes the item produced (what it found, ruled out or checked) and the line that moves `now` on and adds the item to `done` (or to `skip` when it's dropped). Work that turns out bigger adds items to `plan`. This gives each item its own time on the graph and its own notes. A plan is for work the node's owner does itself, item after item. A wave of sub-agents gets no plan: its children are the plan, and each shows its own status. A node with a plan closes with every item in `done` or `skip`.
  - Example: a QA round starts with `{"id":"qa2","p":"qa","t":"Round 2","st":"run","plan":["original repro","buy twice","close mid-animation"],"now":"original repro"}`; after the first scenario `{"id":"qa2","done":["original repro"],"now":"buy twice"}`; a scenario found on the way → `{"id":"qa2","plan":["buy three times in a row"]}`; etc.
  - Anti-example: all scenario nodes appended together when the round ends, so the viewer can't tell how long each took or what the agent did meanwhile.
