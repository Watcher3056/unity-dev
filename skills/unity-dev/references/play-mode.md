# Play Mode runs (reproduction and QA)

Part of the unity-dev skill, read by the main thread, the tester, the reviewer, R&D branches, recipe agents and tool agents (SKILL.md, **Skill files by role**).


The same rules apply whenever the game is run to reproduce a problem (debugging) or to check a change (stage 7), by the main thread or by the tester. The purpose is that the agent runs the needed sequence with the needed timings itself, without complicated manual testing in the Unity window (especially in 3D).

[PM-WHERE] **Where to run it.** Pick what is closest to the real game and still practical:

- **In the actual game.** Take control of the chain: temporary cheats, debug commands, simulated input where the case involves the user's actions, etc. Operate as close as possible to a normal session.
- **When that's too hard or impractical** (long setup, hard navigation, precise timing, etc.): create a separate test scene from the original prefabs, scenes or their parts, Animator controllers, configs, etc., as close to the real case as possible. You don't need a ready-made scene.
- **When even that isn't feasible:** take what you can from the chain and build a synthetic or half-synthetic simulation in a separate scene.

[PM-LEVELS] **Levels of a check.** Each level makes one more thing real; name the level of every check in the report.

| Level | What becomes real at this step | How outside decisions enter | Example (a shop) |
| --- | --- | --- | --- |
| 1. Node | only the part under check: a component, an asset, a controller, etc. | the driver sets its inputs directly | the price calculation with set inputs |
| 2. Object | + the whole object with all its own components | through the object's own calls | the shop prefab with all its scripts, a purchase through its own call |
| 3. Stand | + the systems around the object: managers, navigation, services, other objects, etc. | through the game's own calls | + inventory, wallet and saving in a test scene |
| 4. Sandbox | + decisions of other actors arise by themselves: AI, timers, spawning, etc. | only the player's input is simulated | customers walk in and haggle on their own in a test scene |
| 5. Game | + the real level, content and flow: loading, progression, etc. | only the player's input is simulated | a purchase through the UI in a real session |

- **Known or unknown conditions.** Conditions are known when the evidence shows every step from the start to the symptom. A step the facts left open (which request, which save, which message, etc.) makes them unknown, whatever else is known.
  - Examples: the log shows the purchase request, its response and the empty inventory → known, start low; the log shows the crash but not which of two saves ran before it → unknown, start from the user's session and narrow; etc.
  - Anti-example: treating "the user did X and saw Y" as known conditions while the step that decides the outcome is still a question.
- **A bug with known conditions:** reproduce bottom-up, from the lowest level where the part the evidence points to is real. If it doesn't reproduce with the conditions of the evidence, go one level up; first check that the setup matches the evidence, so the step up doesn't paper over a bad setup. "Not at one level, yes at the next" is itself a finding: the cause is in what the lower level substituted.
- **A bug with unknown conditions:** reproduce where the user saw it, then narrow down to the lowest level where it still happens, for fast iterations.
- **A fix:** "before → after" at the level where the bug reproduced; a confirmation one level up only when it would show something the passed levels and the user's evidence don't (see [PM-START]).
- **A feature:** Stand by default. Node for fast iterations while building it. Sandbox when the feature or bug lives in other actors' decisions (AI behavior, timers, spawning, etc.). Game when it depends on the level, content or flow (saving and loading, transitions between levels, performance on the real scene, etc.), or when the user asks for it.

[PM-OWN-SCENE] **Your own test scene by default.** Build it from the original prefabs and the game's real settings for the chain under check. Existing test scenes in the project are references for how scenes are assembled and initialized, not stands: they are set up for their own purposes (simplified systems, missing equipment, fixed states, etc.), and their quirks cost time and can hide or imitate the bug. Use one as it is only after checking what in it differs from the game for the chain under check; if anything in the chain differs, build your own. The scene you build stays in the project ([PM-SETUP-STAYS]).

- Example: a test scene in the project fakes the save service for a menu feature → for a bug in saving, build your own scene with the real save service and the real save settings, and look at that scene only for how it initializes the managers; etc.
- Anti-example: switching systems inside someone else's test scene one by one until its setup stops getting in the way.

[PM-START] **Start where the evidence says it breaks.** The chain where the bug lives runs from the last point the evidence shows working (the user's logs, facts from stage 2, etc.) to the symptom. Reach that point the quickest way that goes through the game's own code (its entry methods, debug commands, cheats, etc.), instead of replaying everything before it. When new facts move the point, move the reproduction with it. This holds for the reproduction and for QA. A confirmation one level up ([PM-LEVELS]) runs once, at the end of QA, when it would show something the passed levels and the user's evidence don't; it starts from the situation the user's evidence recorded (positions, distances, settings, the order of actions, etc.), not from a search for a situation where the case happens again. Ask: what would this level show that the passed levels and the user's evidence don't? If the answer is "nothing new", or the run can't reach the situation for reasons unrelated to the chain under check (input that doesn't arrive, a load that doesn't finish, an actor that leaves the spot, etc.), don't tune the stand: the result counts at the level reached, the report names that level and why the next one wasn't reached, and the confirmation goes to the user as a manual check: what to do, what to expect, which temporary logs to look at (they stay in place).

- Examples: the logs show the purchase goes through and the inventory doesn't update → start from a completed purchase through the shop's own purchase call, not by walking the character to the shop and through the dialog; the user's report names the level, the loadout and where the character stood → the confirmation starts there; the user's logs show the request is sent and the break is in the inventory update, already checked on the real service → a fight to bring up a test shop with payments shows nothing new; etc.
- Anti-examples: setting the state's fields by hand when the evidence doesn't show that entering the state works (that skips a part where the bug may live); waiting round after round for AI or chance to bring the game into the needed state when the game has its own call that enters it; trying distances and angles one after another until the AI happens to do what the user saw; stepping down a level at the first obstacle when that level is the one that checks the part where the bug may live.

[STAND-PREP] **The stand is prepared from recipes and tools, by several agents, before the tester builds it, and again whenever a later round needs a mechanic it doesn't have.** The tester then works from tested parts instead of finding each missing precondition one round at a time.

- **Mechanics.** The main thread lists the actions the scenarios need, from the spec's situations: spawning an actor, equipping an item, a jump, a purchase, opening a screen, etc. Each is marked as part of the chain under check (it runs for real, [PM-ORIGINAL]) or as setup (it may be set directly). A mechanic already recorded in `.ai-profile/knowledge.md` is reused as it is.
- **Recipes.** One read-only recipe agent per remaining mechanic, in parallel with the fact agents, without Unity. It returns: how the game itself triggers the mechanic (its entry call); where the project already sets it up (scenes, stands, prefabs, tests, debug commands, etc.); the readiness check that proves it worked (every physical part of an actor in place, the item in hand, the screen open, etc.); known pitfalls.
- **Tools.** Then one tool agent per mechanic writes it as a tool in the project's test folder, from its recipe, with the readiness check built in: the tool reports what is off. It doesn't use Unity; where the project allows a compile check outside the Editor (its generated project files, etc.), it compiles its tool there. A tool of a mechanic in the chain under check doesn't bypass it: it puts the character on the pressure plate and lets the game open the door, rather than applying the result directly.
- **The tester's first round** runs every tool's readiness check, fixes what is broken, then builds the scenarios on top of the tools.
- **Later rounds.** Before a round that needs a mechanic the tools don't cover (a review finding, a new situation in the spec, etc.), the tester names it, and the same recipe → tool step runs for it.
- Confirmed recipes go to `.ai-profile/knowledge.md`; tools stay in the project ([PM-SETUP-STAYS]).
- Example: a check of a purchase popup needs "open the shop", "give currency" and "stock an item" → three recipes from the shop's own calls and the existing shop test scene, three tools with the checks "shop open", "balance set", "item listed"; a later round needs "reload the save" → one more recipe and tool; etc.
- Anti-example: the tester writes the whole driver at once and finds one missing precondition per round: no save loaded, then a car whose wheels stayed behind when only its body moved, then a popup opened before its screen loaded.

[PM-STAND] **On the stand, freeze what isn't in the chain under check and put the participants in known positions.** Other actors' decisions (AI, timers, spawning, etc.), the player's input and the camera are switched off or set directly when they aren't part of what's checked; participants start in known positions and in poses taken from real frames of the action; after each attempt a probe logs what the action actually hit or changed (object, collider or element, point, owner, etc.), so a miss shows in the attempt itself. The player stays when the changed code is the player's own ability (it reads the camera, the aim, the equipment, etc.): hold it still by setting its position and aim directly. The round report names what was frozen; when a frozen part can change the outcome, the confirmation one level up ([PM-START]) runs it live. The stand itself: [STAND-PREP]. Before any scenario the driver runs the readiness checks, and a failed check stops the round with what is off. An action whose hit is under check (a projectile, a beam, a swipe, etc.) starts next to its target, with a known point and direction: a miss then means the detection, not the aim.

- Examples: a check of how a projectile picks its target behind cover → shooter and target in fixed poses, the target's AI planner off, a probe logs the first collider the shot met; a bug in an item card → the card opens directly with the needed item instead of a walk through three menus; etc.
- Anti-examples, freezes that give a false PASS: the change or the complaint is about what gets hit or chosen (which collider, which target, which slot, etc.), and the stand calls the handler directly instead of the real query, skipping the part under check ([PM-ORIGINAL]); the complaint is about live interaction (AI decisions, timing between actors, physics over time, etc.), and the stand freezes it, though that is the Sandbox level's work ([PM-LEVELS]); a pose that never happens in play is checked, such as a collider active only during part of an animation, posed outside that part.

[PM-BUILD] **Build what's missing.** Write whatever the run needs: test scenes, scripts, controllers, mocks, cheats, spawners, etc. Drive the game with whatever works (Unity MCP, test runner, debug commands, simulated input, etc.). If no editor is open, launch Unity yourself. In a test setup, change only test setup; if the test rig itself is broken, fix the rig and say so.

**Observe through logs, act through commands:**

- [PM-LOGS] **Logs observe.** What the game does is observed through temporary logs in the real code, tagged with something greppable (e.g. `[TMP-<task>]`) and written from the start of the run. Log the values that tell hypotheses or scenarios apart at the points where the outcome is decided: state transitions, which condition failed, values before and after each step that changes the result, values every frame where they change continuously, etc. For each logging point, know what each possible value would prove. Read the logs after the run and correlate events by identity: match the objects involved (IDs, transactions, state transitions, etc.), don't infer how many times something happened from repeated callbacks, and don't merge checks that only have similar names. The logs stay until the user accepts the result and are removed before commit. Reading them: [PM-OUTPUT].
- [PM-COMMANDS] **Commands act.** Commands through a bridge are for setup (open a scene, place and configure objects, etc.), starting and stopping Play Mode, simulating the user's input (a key press, a click, a gamepad move, etc.), one-off reads of values that don't change during the run (a config, a serialized field, etc.), reading the logs afterwards, etc. Batch them (the bridge's batch call, etc.) only when they don't depend on game time.
- [PM-DRIVER] **A driver runs the whole sequence inside the game, one attempt at a time.** Anything that depends on the game's state (initialization, loading, animations, AI decisions, etc.) runs inside the game as one sequence; the agent starts it, waits once ([PM-WAIT-ONCE]) and reads the outcome. Pick the form by how settled the scenario is:
  - **still being found** (what to set up, what to watch, etc.) → one bridge call per attempt that starts the whole sequence inside the game (a coroutine, an async task, etc.), when the bridge can run code that keeps running in the game; nothing to recompile;
  - **settled and run again** (before → after, repeats, other values, etc.) → a driver script in the scene, compiled once; what changes between runs (values, counts, which object, etc.) comes from a settings file, and the repeats run in one Play Mode session, resetting the stand between them.

  Each step waits for a game condition, not for a pause, has its own wait limit, and logs a progress mark; when a step misses, the driver logs the step and the state it saw. It writes its progress marks, its results and the end mark to a file of its own under `.ai-profile/work/<task-id>/out/` as well as the log, so the wait has one place to watch ([PM-WAIT-ONCE]). A miss is fixed and the whole attempt runs again, instead of continuing it from outside step by step: every call from outside is a full agent step.
  - Example: checking a fix in loading a save → while the scenario is still being found, one call starts "load the slot → wait for the level → open the inventory → log the item count → end mark"; once it's settled, the script takes the slots and the repeat count from a file and runs them all in one Play Mode session; etc.
  - Anti-example: "load", "is it loaded?", "open the inventory", "read the count" as four separate calls, repeated for every attempt.
- [PM-WAIT-ONCE] **Wait once, not by polling.** Wait for a round with one call that returns on whichever comes first: the end mark in the log, an error or exception in the log, Play Mode stopping, the Editor or bridge disconnecting, no new progress mark for longer than a step can take, or a time limit above the round's expected duration plus a margin. Every outcome returns control with its reason. The skill's `scripts/wait_for.py` is that call: it watches the driver's result file or the log inside one command and returns with a short summary on the end mark, an error line, a stall (no progress mark for longer than a step can take) or the time limit; give the tool call a time limit above the wait's. The polling happens inside that one command, not over the agent's steps.
- Example: the driver waits until the character is initialized, triggers the event the way the game does, waits until the expected state is entered, logs the values and an end mark; the agent starts the round, waits once, then reads the log. A miss reads "step 3: expected state not reached, state = …"; etc.
- Anti-examples:
  - the photographer: "trigger the event, wait, read the value" as separate commands. The agent samples the game every few seconds of real time and misses the moment it needs; a short in-game window passes between two commands;
  - following a value that changes during the run through repeated live queries instead of a log;
  - reading the console again and again until the result shows up: every read is a full agent step;
  - sending commands one after another with pauses, hoping the game keeps up with them;
  - etc.
- [PM-OUTPUT] **A short answer in the context, the full one in a file.** A bridge call or a log read returns, in a line, what the step was run for: the values it checks, counts (errors, warnings, the tag's lines, etc.), and the path of a file under `.ai-profile/work/<task-id>/out/` that holds everything bigger (dumps, object state, the full console, stack traces, etc.). When the line says something is off (an error, a count that differs, an unexpected value), open the file and search it by the tag or the error instead of reading it whole. Nothing is lost: it's all on disk, and the context gets what decides the next step. Every line read stays in the context, and compressing it costs re-reading the code.
  - Example: "round 2: slot 3 loaded, items 12→12, errors 1 → out/round2.txt", then only the stack of that one error; etc.
  - Anti-examples: the full console with stack traces after every step; a snippet that returns a whole object hierarchy to find one value in it.
- [PM-COMPILE] **Waiting for compilation is one call, for every role.** After a change to scripts or assets, refresh, compile and wait until the editor is ready for tools in one call: the bridge's own refresh with waiting (e.g. CoplayDev's `refresh_unity` with a compile request and `wait_for_ready`), the batch-mode compile run without a bridge, etc. If it returns not ready, read the compile errors once ([PM-OUTPUT]).
  - Anti-example: a refresh through a code snippet, then a fixed sleep, a read of the editor state, another sleep, again and again.

**Run it efficiently:**

- The open Editor and its bridge: [editor.md](editor.md) ([PM-EDITOR], [PM-SHARED-EDITOR], [PM-WINDOW]).
- [PM-SESSION] **One Play Mode session per round.** A round runs every scenario in one Play Mode session, in order, logging a result per scenario: the "before" and "after" passes too, when the game state can be reset between them (respawn the objects, reset the systems the scenarios use, etc.). Other scenes load inside that session when needed. Every extra session pays entering and leaving Play Mode, and without a bridge every extra launch pays Unity startup too. Separate sessions are for debugging the driver itself, or when the state can't be reset between passes.
- [PM-LANES] **Independent scenarios run side by side in one session.** Scenarios that share no state (no common object, pool entry, manager state, timer or zone) each get a lane: a copy of the stand placed apart or on its own layer, its own actors, its own tag in every log line and its own camera; the readiness checks run per lane. Scenarios that share state, or whose effects reach other lanes (area effects, pooled objects, etc.), stay sequential. The round report names the lanes. In every profile that runs QA.
  - Example: three doors in one scene at once, one opened by a key, one by a lever, one by a plate; etc.
  - Anti-example: two lanes sharing one pooled popup, so the second scenario measures the first one's object.
- [PM-STUCK] **A stuck scenario doesn't hold the others.** While one scenario's setup is being fixed, the scenarios that don't depend on it run in the same sessions. Debugging one scenario's driver is not a reason to leave the rest for the end.
  - Example: the checkout scenario can't reach payment yet → the cart and profile scenarios, which don't need payment, still run in the same session; etc.
  - Anti-example: a long series of sessions spent making one scenario valid, with the independent scenarios queued behind it.
- [PM-SETUP-STAYS] **Leave the setup in place.** Test scenes, scripts, mocks, etc. stay in the project: every reproduction and QA round reuses them, and the user removes them. List them in the final report. Record in `.ai-profile/knowledge.md` how to bring this project's objects into a testable state (what a test scene needs, what to configure, what to wait for, etc.), so the next task starts from there.
- [PM-REPRO-IS-QA] **The reproduction is the QA setup.** The setup that reproduced the problem before the change is the one QA uses after it.

**Hard rules:**

- [PM-ORIGINAL] **The part under check stays original.** The changed part and the chain where the bug lives run the way the game runs them; substitutes go only around them. Ask: would this run fail if the fix were wrong? Does it run the same code path as the real case? What doesn't it exercise (simplified controllers, missing managers, different timing, different scene setup, etc.)? A run that substitutes the part under check can explain a mechanism, but it is neither a reproduction nor a verification; label it as such. Whatever a question the facts left open is about (which object, which call, which state, which message, etc.) belongs to that chain and stays original: the answer lives in it. A mechanism shown on substitutes is Real at most ([FIND-STATUS]).
  - Examples: the facts left open which request cleared the session, and the client's own retries could be one → the run uses the real client with its retry logic, not a stub that sends one request; the facts left open which save overwrote the profile → both real save paths run, not a fake that writes once; etc.
  - Anti-examples: replacing the object the open question is about with a stand-in, showing that "something else can do it", and calling that the cause; a fixture that leaves out the parts of the real object the question is about (child objects, attached components, event listeners, etc.).
- A run that shows a culprit is involved doesn't show which of its parts is at fault ([CAUSE-PARTS] in [findings.md](findings.md)).
- [PM-BEFORE-AFTER] **Same setup before and after; the comparison decides pass or fail.** Reproduce the problem before the change and verify after it in the same setup, with the same measurements. Each scenario's result is the pair "before → after" for the values that describe it (positions, timings, states, outcomes, etc.). PASS means the behavior stayed the same, or changed exactly as intended. Any other difference is a FAIL or a finding, even when the scenario itself ran to the end. Which situations get a "before", and whether its values are measured or only seen, follows the profile ([PROFILE-STAGES], in the brief).
  - Examples: the change targeted a menu, and a jump that reached 1.2 m before now reaches 0.4 m → finding; the fix was meant to let a door open, and it stayed closed before and opens after → the intended change, PASS; etc.
  - Anti-examples: "the animation started and finished in both runs → PASS" (that proves the scenario ran, not that it behaves the same); a check written to accept either of two different outcomes, so a changed outcome can't fail; values logged in both runs but never put side by side.
- [PM-CAN-FAIL] **A comparison counts only if it could have shown the break.** What to measure follows from the change: what it touches directly, what depends on that, and on along the chain to what the player or user notices. Before concluding "no difference", ask: if this had broken, would my number have changed? A value that is equal in both runs by construction proves nothing.
  - Examples: damage rounding changed → damage per hit → hits to kill → whether a boss phase still triggers at its health threshold; a panel got narrower → its size → whether its text wraps → whether the button below it is still visible and clickable; etc.
  - Anti-examples: two channels removed from a mixer group, the volume of the channels that stayed in the group compared, and "the sound didn't change" reported; a search filter changed, and the page count, which the filter doesn't affect, compared.
- [PM-OBSTACLE] **An obstacle in the setup is setup work, not a stop.** Something the scenario needs is missing or set up differently than in the game (a ready-made scene, objects, systems, data, preconditions, etc.), or a system won't start in a test scene: find why the scenario doesn't happen, change the setup, run again. Every scenario ends as pass or fail; "not run" is not a result. The only exceptions: the obstacle sits inside the part under check (then it's a finding), or it's a blocker of [AUTONOMY] in SKILL.md.
