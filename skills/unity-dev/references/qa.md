# QA (stage 7)

Part of the unity-dev skill, read by the main thread and the tester (SKILL.md, **Skill files by role**). The stage itself is [PIPE-QA] in SKILL.md; these are its rules. How to run the game is in [play-mode.md](play-mode.md); the breadth of the round follows the task's profile ([PROFILE-STAGES] in [profiles.md](profiles.md)).

- The tester sub-agent does manual QA in Play Mode: the scenarios the profile's QA cell sets ([PROFILE-STAGES]), named in the brief: the original reproduction, the acceptance scenarios in the user's words (confirmed in stage 4), their repeats, what the change touched, etc. Before measuring, it extends the base setup from stage 6a for the review's open findings, then runs every scenario in one round.
- [QA-REPORT] It reports per scenario pass / fail, with the "before → after" values where the profile measures them ([PM-BEFORE-AFTER] in [play-mode.md](play-mode.md)) and the evidence [QA-EVIDENCE] sets.
- [QA-EVIDENCE] **The user is shown what changed in the product's own picture, from the view that shows it best.** For the result the user is shown, not for every scenario: a recording before and after where it happens over time, a picture where it is a state. The viewpoint is free, the user's own or another, whichever shows the outcome better and is easier to capture; the user's render camera settings and pipeline are required. The user gets the recording itself, not frames cut from it. Pass or fail is decided by what answers it best: the logs where the result is a number or a state, the recording where it is how it looks.
  - Examples: a car drifts off its lane → a recording from a chase camera with the game camera's settings, both lanes in frame; pass or fail by the logged offset; list items jump as one is dragged → a recording of the screen as the user sees it; a coupon total → the cart screen before and after, pass or fail by the totals in the log; etc.
  - Anti-examples: two cars colliding filmed only from the driver's seat, so nobody can tell where each one was; frames cut from the recording pasted into the answer instead of the recording; frames read to find a number the log already printed.
- [QA-SCEN] **Scenarios come from the change, not only the symptom.** QA checks that the change does what was asked (a fix, a feature, a changed behavior, a refactor that keeps it, etc.) and that nothing around it broke. A round runs what the profile's QA cell names ([PROFILE-STAGES]): in Deep the whole list; in Normal the rest of it is a round of its own when the user asks. Combine:
  - **transitions:** every way into and out of the changed behavior (from neighbouring states, on interrupts, on re-entry), not only its steady state;
  - **repetition and history:** run the scenario several times in a row and after related events (interrupts, state changes elsewhere, a reload or respawn, etc.); many bugs appear only the second time;
  - **impact:** everything else that uses what the diff changed (assets, classes, components, settings, etc.);
  - **risks:** what else the change can affect that reading the code can't predict (the critics name some). A limitation the choice named (the user took the form knowing it) isn't a scenario, the report repeats it; one closed in the form is part of the change and is checked;
  - **review findings:** each open finding from stage 6 becomes a scenario with its expected "before → after", except a limitation the choice named;
  - [QA-INVARIANTS] **invariants:** facts about the changed behavior that must stay true whatever the player does before, during and after it. Take them from this project (code, docs, design, the task), then check them across varied or randomized action sequences when something can drive the game.
    - Examples: the design says the pause menu can be closed at any moment → it closes at random moments, including mid-transition; the shop code clamps currency at zero → no sequence of purchases and refunds makes it negative; etc.
    - Anti-examples: a general assumption that isn't this project's rule, e.g. "every window can be closed" (a game can have a deliberately unskippable step) or "resources never go negative" (a game can allow debt); a single check, e.g. "it worked once" (that's a scenario, not a rule that holds across sequences).
  - Examples: a new co-op lobby → players create, join and leave a lobby, and the solo menu sharing its screen still works; a save format changed → old saves load and the cloud sync reading the same files still works, while the known limitation «saves from before version 2 lose their thumbnail» isn't run; etc.
  - Anti-examples: QA runs a limitation the choice already named and reports it as a failure; QA checks only the new feature's own flow and never the screens that share the changed component.
- [QA-REPEAT] **The main measurement repeats after related events.** The measurement of what was fixed or changed runs again within the same round after each related event (a reaction, an interrupt, a state change, a re-entry, etc.), not only once at the start. Passing on first entry doesn't mean passing.
  - Example: the discount calculation changed → the cart total before and after applying a coupon, after removing it, after applying it again; etc.
  - Anti-example: measuring the main value once at the start, and after the events only checking that the state came back.
- [QA-ROUND] **One round, one report, one version of fixes.** A round runs every scenario and reports once, with every scenario's result; a failure doesn't stop the round ([PM-STUCK] in [play-mode.md](play-mode.md)). Everything the round found that the chosen variant fixes is fixed in one version; that version goes through review once, then QA runs everything again within the round ([AUTONOMY] in SKILL.md). A failure that needs another variant ends the round ([QA-FAILED]). Sending each finding back on its own, as it comes, costs a full loop of fix, review and setup per finding.
  - Example: a round finds a wrong total and a missing receipt → both are fixed in one version, reviewed once, and QA runs every scenario again; etc.
  - Anti-example: stopping the round at the first failure, fixing it, reviewing it, rebuilding the setup, and finding the second failure an hour later.
- [QA-NO-FIX] It doesn't fix what it finds; failures go back to the main thread. Only if Unity can't be launched at all, it writes a short QA checklist for the user and checks the logs from the user's run.
- [QA-FAILED] **QA failed:** a failure the chosen variant fixes (a value, a missed call, the wiring, etc.) is fixed in one version and QA runs again within the round ([QA-ROUND]), while the corrections lead somewhere ([LOOP-STOP] in [agents.md](agents.md)); one that needs another form, another reading or a new R&D ends the round with the report: what failed, the evidence, the options for the next round (investigation or R&D for the failing part, another candidate, etc.); the user picks it ([AUTONOMY] in SKILL.md). Don't report the task as done.
- [QA-UNVERIFIED] **"Not verified" is not done.** A scenario the tester reports as not verified, limited or not run (an obstacle in the setup, an error in its own test code, etc.) goes back to the tester as setup work, the same way a failure goes back to investigation. The round ends only when every scenario it runs is pass or fail, or at an exception of [PM-OBSTACLE] in [play-mode.md](play-mode.md). Naming the limits honestly belongs in the final report after that, not in place of the check.
  - Example: the check of a neighbouring screen throws in the test's own code → fix the test and run it again; etc.
  - Anti-example: the main scenario passed twice, the remaining ones are listed as "not verified" in the report, and the task is closed.
