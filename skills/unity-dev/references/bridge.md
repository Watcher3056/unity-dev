# The editor bridge (MCP for Unity)

Part of the unity-dev skill, read by the main thread (SKILL.md, **Skill files by role**): installing, connecting and updating the bridge is its work at the start of a task. How every role works through an open Editor and its bridge is [PM-EDITOR] in [editor.md](editor.md).

- [PM-BRIDGE] **No bridge in the project: install MCP for Unity by CoplayDev at the start of the task, without asking (the user's rule, 2026-10-15).** The project already has a bridge when its `Packages/manifest.json` lists a Unity MCP or editor-bridge package (any vendor): then use that one. A server in the user's agent config alone is not a bridge: it sees no Editor until the package is in the project (three live tasks ran with the server configured and no package, and every script reload went through a debugger). Otherwise install CoplayDev's MCP for Unity (the default bridge) at once, in parallel with the stages that don't need Unity, and say in the first answer what was changed, so the user can undo it; the first Play Mode run waits for the bridge, not the other way round.
  - What it changes, to tell the user: a package in the project (`com.coplaydev.unity-mcp` from `https://github.com/CoplayDev/unity-mcp.git?path=/MCPForUnity#<release>`: the latest release at install time, pinned); a Python MCP server for the agent (`mcpforunityserver` at the same version, in its own virtual environment: on Windows `uvx` can fail on a locked file); {{bridge-config-change}}.
- [PM-BRIDGE-CONNECT] **One connection, in the project, under its own name.** Connect the server over stdio in {{mcp-project-config}}, under a name of its own (e.g. `unityBridge`), never `unityMCP`{{mcp-config-file}} {{bridge-auto-register}}
  - **Check it.** Back up every config before changing it. Afterwards {{mcp-check}}
  - {{mcp-approval}}
  - Record the installed version and the setup in `.ai-profile/knowledge.md`.
- [PM-BRIDGE-UPDATE] **A newer release of the installed bridge:** at the start of a task, check the bridge's latest release (its git tags, the server's package index, etc.). If it is newer than the installed one, offer in the first answer: update / not now (the default) / don't offer again in this project. Before updating, say what the new release changes in its dependencies and in the user's config; update the package and the server to the same version, and run the same check.
  - "Don't offer again" goes into `.ai-profile/knowledge.md` and is read at stage 0; it stays until the user asks to take it back.
