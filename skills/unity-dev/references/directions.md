# Directions

Part of the unity-dev skill, read by the main thread, R&D branches, critics, the judge, the reviewer and implementers (SKILL.md, **Skill files by role**); [RND-EXISTING] and [DIR-USUAL] serve R&D only (`roles.json`). These are directions, not hard rules: situational, with the challenge questions they imply. [RND-EXISTING] is the exception: a rule of R&D, whose branch runs wherever its condition holds.

- [DIR-EXISTING] **Existing vs new.** Look at what the project already has that covers part of the task: similar features, shared checks, settings assets, pipelines, etc. Extending fits when it's the same concept and the owner stays coherent. A separate component or system fits when extending would mix independent behaviors, bloat an owner or tie unrelated lifecycles together. Building something parallel to an existing pipeline needs a reason you can state.
- [RND-EXISTING] **What exists comes first.** When the project already has a variant of what's needed (another preset, another material, a setting, etc.), or the cause sits in content (a clip, a curve, an import setting, etc.), one branch uses that: switch to the existing variant, or edit the content, and say who makes that edit (the agent, an animator, a designer, etc.). A new mechanism that works around it (a clamp, a runtime override, etc.) is its own branch, with its cost: where it runs and what else passes through it.
  - Examples: a notification sound is too loud and the project has a quieter preset → a branch "use the quieter preset"; a crate bounces too high and the project has a less bouncy physics material → a branch "use that material"; etc.
  - Anti-example: only code branches that cap the volume at runtime, with a new script on every sound source.
- [DIR-USUAL] **The field's usual techniques are one source of R&D directions, and an unusual one stays open.** Next to what the project has, the smallest change ([RND-MINIMAL]) and a rejected assumption ([RND-CHALLENGER]), ask in every profile: what are the field's usual techniques for this class of problem (a burst of input absorbed before it is sent, a repeated write made harmless where it lands, a slow lookup answered from an index, etc.)? Name each by the level it acts at, not a place (the work done per request, not the class that runs it; a batch prepared ahead, the data layout, the screen, etc.) and compare it with the branches at that level: a branch covers a technique only where it uses it, not by acting at the same level. One not among the directions gets a branch, or the comparison says why not (the project can't carry it, a branch already uses it, etc.). Is an unusual direction worth a branch here? Any of them can be any branch, the first idea or not, and enters by its principle ([RND-DIRECTIONS]).
  - Example: a long list stutters while scrolling, and both directions load its data in pages (the data source) → reusing the row views acts on their drawing, another level: it gets a branch, or the comparison says why not; etc. Example: a technique that needs a service the project doesn't run → the comparison says so, no branch; etc.
  - Anti-example: "that technique is already a branch" said of a branch acting at another level, or at the same level with another technique (a branch that caps a slow query's rows, where an index answers it in full); a technique given as a mechanism and a place ("a debounce in the search controller"), so the branch only dresses it; a direction dropped only because it isn't the usual one.
- [DIR-STATE] **Added state, flags and checks.** Each should answer "which scenario needs this?" Before adding a long gate, ask: does an existing check already cover it? Will the gate still hold when a new state is added? Long multi-condition gates tend to be fragile.
- [DIR-FRAGILE] **Fragile systems.** Large core systems with many callers need extra care. Identify them from project docs and history, e.g. movement, animation drivers, AI planners, save systems. Trace callers and check history for earlier fixes. A fix for one bug often caused another, so don't bring old regressions back.
- [DIR-CONFIG] **Configurability.** Values a designer will plausibly tune usually belong in serialized fields, profiles or ScriptableObjects with sane defaults. Constants are fine for values nobody should tune.
