# The scout's map

Part of the unity-dev skill, read by the scout (SKILL.md, **Skill files by role**). The map is what every later stage builds on: the spec's situations, the fact items, the direction sheet's analogue row ([RND-DIRS] in [profiles.md](profiles.md)), the branches' precedents.

- [SCOUT-LINKS] **Every link of the chain comes with the other cases it already handles, and how.** Goal: the direction a senior engineer sees first, "do it here the way this link already does it for its other objects", can't be lost later because nobody wrote the precedent down. The map holds a table, one row per link of the end-to-end chain: the link (a method, a handler, a setting, a schema, a config, a pipeline definition, a stylesheet, a declarative asset, etc., with its file:line or path; a link that is data or configuration rather than code gets its row like any other: what it declares, for whom); the other objects, inputs or cases it already handles (other callers, other sources, other states, other item kinds, other request types, etc.); how it handles each (the branch it takes, the value it uses, the guard it applies, the entry it declares, etc., with file:line); the ways into the link (the states, callers or events it is entered from, with where); and the task's case in that link, with how it differs there. A link with no other case says so, with the search that showed it, or what it couldn't read and why; for new behaviour the rows are the links of the nearest existing kind ([RND-DIRS] in [profiles.md](profiles.md)). The chain's entry point and the state it needs stay the fact agent's ([FACTS-ENTRY] in SKILL.md); this table gives the ways into each link. The table is facts, not a proposal: it names no fix. The table stays short: names, places and a few words per cell; what a row rests on goes under it in a line, and what needs reading beyond the map is a fact item ([PIPE-FACTS] in SKILL.md), so that the map is read whole in one call. Challenge questions: for this link, who else calls it, and with what? → a row per caller or case. Does the task's case go through a branch the others don't, or skip one they take? → say which, with the line.
  - Example: a request's rate limiter → "the limiter: `Throttle.Apply` (api/throttle.go:40); handles: the public API by key (44–60), the admin API by IP (62–70), webhooks exempt (72); the task's case: the import endpoint has no row and falls to the default bucket (75)"; etc.
  - Example: a file importer → "the parser: `Import.Parse` (import/parse.py:30); handles: CSV with a delimiter guess (80–120), JSON with a schema check (130–160), XML with an XSD (170–200); entered from: the upload form and the nightly job (api/upload.py:12, jobs/nightly.py:40); the task's case: TSV, no row, read as CSV with the wrong delimiter (85)"; etc.
  - Example: a deployment pipeline's stage, data rather than code → "the deploy stage: `.ci/pipeline.yml:40`; serves: the web service with a canary (44–52), the worker with a blue/green switch (54–60); entered from: the test stage's success and a manual trigger (62–66); the task's case: the new scheduled job has no stage of its own and runs through the web service's canary (46)"; etc.
  - Anti-example: a map that lists the chain's links and "similar implementations" by name only, so the sheet's analogue row has nothing to quote and the first wave starts from the first idea alone.
